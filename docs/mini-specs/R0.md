## 2. Goal (Mục tiêu phase)

> Chuẩn hóa contract cấu hình xác thực sang một tên biến duy nhất `AUTH_SECRET`, triệt tiêu hoàn toàn các chuỗi bí mật dự phòng mặc định ở runtime và docker-compose, bảo đảm hệ thống fail-closed và phản ánh đúng trạng thái readiness khi cấu hình thiếu/sai, trong khi vẫn giữ luồng đăng nhập hợp lệ hoạt động và tiến trình build độc lập với production secret.

## 3. Constraints (Guardrails bắt buộc)

1. **Một contract tên biến duy nhất:** Chỉ dùng `AUTH_SECRET` cho toàn bộ mã nguồn, cấu hình compose, tệp ví dụ và tài liệu triển khai. Không tạo alias hoặc fallback ngầm từ `JWT_SECRET`.
2. **Zero-Fallback Runtime & Compose:** Không có chuỗi secret mặc định viết cứng trong code (`session.ts`) hoặc trong các file compose (`docker-compose.prod.yml`, `docker-compose.yml`).
3. **Local Dev Explicit Secret:** Môi trường dev cục bộ phải tự sinh secret riêng vào tệp môi trường được gitignore (`.env`), không dựa vào fallback có sẵn trong repository.
4. **Tách biệt Build-time và Runtime:** Lệnh `npm run build` và Docker build stage không yêu cầu `AUTH_SECRET` production và không được fail chỉ vì thiếu secret lúc build.
5. **Không lộ secret:** Không đưa secret thật, tiền tố secret, hash/fingerprint, hoặc toàn bộ `process.env` vào Dockerfile, image layers, repository, client bundle, response HTTP hoặc structured logs.
6. **Không tự biến đổi secret âm thầm:** Không dùng `.trim()` để âm thầm sửa secret có khoảng trắng đầu/cuối. Nếu secret chứa whitespace thừa, từ chối ngay lập tức; nếu hợp lệ, dùng chính xác từng byte cấu hình để ký.
7. **Rõ ràng về Entropy:** Quy định độ dài tối thiểu 32 ký tự và danh sách đen (blacklist) chỉ là lớp kiểm tra tính hợp lệ cơ bản chống cấu hình nhầm, không thay thế cho yêu cầu sinh khóa ngẫu nhiên mật mã (`crypto.randomBytes` / `openssl rand`).
8. **Fail-Closed kèm Observability:** Khi thiếu hoặc sai secret, runtime xác thực từ chối hoạt động (fail-closed); endpoint `/api/health` phải phản ánh trạng thái `unhealthy` / `unready` (HTTP 503) để ngăn bộ cân bằng tải / reverse proxy chuyển traffic vào container hỏng auth.
9. **Không xâm lấn Schema / DB:** Không thêm cột DB, không migration schema, không tự động đổi password của bất kỳ database nào đang tồn tại.
10. **Bảo toàn hiện trạng:** Không sửa đổi hoặc untrack tệp `docs/HIEN_TRANG_DU_AN.md`.
11. **Ghi nhận F08 riêng:** Không tuyên bố R0 giải quyết bài toán thu hồi phiên (session revocation) hay kiểm tra trạng thái tài khoản thời gian thực; ghi nhận rõ F08 là follow-up ticket.

## 4. Scope (Phạm vi implementation)

### A. Domain Model & Configuration Contract
- Không thay đổi schema DB Drizzle (`src/lib/db/schema.ts`).
- Giữ nguyên interface `SessionUser`:
  ```ts
  export interface SessionUser {
    id: number;
    email: string;
    displayName: string;
    role: 'ADMIN' | 'EDITOR' | 'COOK';
    exp: number;
  }
  ```
- Định nghĩa lớp lỗi cấu hình xác thực `AuthConfigurationError` có kiểu rõ ràng.
- Xây dựng chính sách kiểm tra cấu hình secret tại runtime (`validateAuthSecret(value)`):
  - Undefined, rỗng, hoặc chỉ chứa khoảng trắng: Ném lỗi `AuthConfigurationError`.
  - Chứa khoảng trắng ở đầu hoặc cuối (`secret !== secret.trim()`): Ném lỗi `AuthConfigurationError` (chống biến đổi âm thầm).
  - Độ dài nhỏ hơn 32 ký tự: Ném lỗi `AuthConfigurationError`.
  - Khớp với danh sách đen các chuỗi placeholder đã biết: Ném lỗi `AuthConfigurationError`.

### B. Service / Engine (`src/lib/auth/session.ts`)
- **Loại bỏ hằng số top-level `SECRET`:** Không đọc `process.env.AUTH_SECRET` khi nạp file vào bộ nhớ.
- **Hàm `getAuthSecret(): string` (Lazy Evaluation):** Chỉ đọc và kiểm tra `process.env.AUTH_SECRET` khi các thao tác xác thực thực sự được gọi.
- **Quản lý HMAC CryptoKey:** Nhập khóa `crypto.subtle.importKey()` theo từng giá trị secret hợp lệ, không dùng cache tĩnh làm sai lệch vòng đời test hoặc xoay vòng khóa.
- **Hàm `signToken()` & `setSessionCookie()`:** Gọi `getAuthSecret()`. Nếu cấu hình không hợp lệ, lập tức dừng tiến trình ký và ném `AuthConfigurationError`.
- **Hàm `verifyToken()`:** Gọi `getAuthSecret()`. Nếu cấu hình không hợp lệ hoặc token hỏng/sai chữ ký/quá hạn, trả về `null` an toàn. Phân biệt log lỗi cấu hình hệ thống với việc từ chối một cookie hỏng thông thường từ client.

### C. API Contract & Observability
- **`/api/auth/login` (POST):**
  - Bắt lỗi `AuthConfigurationError`: Ghi log có cấu trúc thông qua `logger.error()`, trả HTTP 500 kèm thông báo tiếng Việt tổng quát: `{"error": "Lỗi cấu hình xác thực hệ thống"}`. Tuyệt đối không trả về stack trace hoặc giá trị biến môi trường.
- **`/api/auth/me` (GET):**
  - Khi token không hợp lệ hoặc cấu hình lỗi: Trả HTTP 200 `{"user": null}` theo contract hiện tại.
- **`/api/health` (GET):**
  - Bổ sung kiểm tra tính sẵn sàng của hệ thống xác thực (Auth Readiness Probe).
  - Nếu `AUTH_SECRET` thiếu hoặc không hợp lệ: Trả HTTP 503 Service Unavailable, payload `{"status": "unhealthy", "auth": "unconfigured", ...}` để Caddy và container orchestration nhận diện ứng dụng chưa sẵn sàng phục vụ.
- **`src/proxy.ts` (Next.js Edge Proxy):**
  - Khi `verifyToken` trả về `null` trên route yêu cầu đăng nhập: Chuyển hướng an toàn về `/login?from=...`, không tạo vòng lặp chuyển hướng.

### D. UI Surfaces
- Không thay đổi giao diện `/login` (giữ nguyên layout Warm Kitchen và các luồng phản hồi người dùng hiện hữu).

### E. Infrastructure & Deployment
- **`docker-compose.prod.yml`:**
  - Đổi `JWT_SECRET` thành `AUTH_SECRET: ${AUTH_SECRET:?Lỗi: Biến AUTH_SECRET là bắt buộc cho môi trường Production}`.
  - Chuyển `POSTGRES_PASSWORD` thành `${POSTGRES_PASSWORD:?Lỗi: Biến POSTGRES_PASSWORD là bắt buộc cho môi trường Production}`.
  - Cập nhật biến `DATABASE_URL` sử dụng `${POSTGRES_PASSWORD}` bắt buộc.
- **`docker-compose.yml` (dev):**
  - Bổ sung `AUTH_SECRET: ${AUTH_SECRET:?Lỗi: Cần cung cấp AUTH_SECRET trong .env (tối thiểu 32 ký tự ngẫu nhiên)}`.
  - Không dùng fallback giá trị mặc định cho `AUTH_SECRET`.
- **`.env.example`:**
  - Hướng dẫn rõ ràng: `AUTH_SECRET` bắt buộc phải là chuỗi ngẫu nhiên mật mã (khuyến nghị lệnh `openssl rand -base64 32` hoặc `openssl rand -hex 32`), tối thiểu 32 ký tự.
- **`scripts/deploy_production.sh`:**
  - Nếu thiếu `.env.production`: Dừng lại và báo lỗi ngay (exit 1), **không tự động sao chép từ `.env.example` rồi chạy tiếp**.
  - Đồng bộ cờ `--env-file .env.production` cho toàn bộ các lệnh `docker compose`.
  - Kiểm tra cú pháp compose an toàn bằng `docker compose --env-file .env.production -f docker-compose.prod.yml config --quiet`, không in output chứa secret đã render ra log.
  - Thay thế user/database hardcoded trong lệnh chạy migration bằng biến `${POSTGRES_USER:-angimom}` và `${POSTGRES_DB:-angimom_prod}`.
- **`docs/PRODUCTION_DEPLOYMENT_GUIDE.md`:**
  - Thay đổi toàn bộ các tham chiếu `JWT_SECRET` thành `AUTH_SECRET`.
  - Hướng dẫn sinh khóa ngẫu nhiên chuẩn mật mã.

## 6. Design Choice (Thiết kế được chọn)

- **Phương án chọn:** **"Lazy Runtime Secret Provider + Fail-Closed Readiness + Strict Compose Contract"**
- **Lý do lựa chọn:**
  1. *Khắc phục triệt để lỗ hổng:* Triệt tiêu 100% đường dẫn rơi về secret mặc định ở cả tầng ứng dụng và tầng điều phối container.
  2. *Bảo vệ quá trình Build:* Tránh lỗi build khi Next.js biên dịch các trang tĩnh/động mà không có secret production.
  3. *Bảo vệ vận hành (Readiness Protection):* Container lỗi cấu hình sẽ không được coi là `healthy`, ngăn Caddy điều hướng người dùng vào phiên bản lỗi.
  4. *Giữ nguyên phạm vi an toàn:* Không thay đổi cấu trúc bảng `users`, không đụng chạm đến cơ chế mã hóa mật khẩu `scrypt` đã ổn định tại AG-11.
- **Các phương án bị bác bỏ:**
  - *Bác bỏ Fallback Dev:* Không cấp secret mặc định cho local dev trong compose vì vi phạm nguyên tắc Zero-Fallback.
  - *Bác bỏ Auto-generate Secret at Boot:* Không tự sinh chuỗi ngẫu nhiên tạm thời khi thiếu secret, vì sẽ làm mất toàn bộ phiên đăng nhập của người dùng mỗi khi container khởi động lại và che giấu lỗi cấu hình của operator.
  - *Bác bỏ Rewrite sang NextAuth/IronSession:* Không cần thiết, làm phình to scope và gây rủi ro hồi quy (regression) trên các luồng đã kiểm chứng.

## 7. Test Plan & Bằng chứng nghiệm thu

Test suite được viết trong file mới `src/scripts/test_auth_hardening.ts`, chạy bằng lệnh `npx tsx src/scripts/test_auth_hardening.ts`. Mỗi ca kiểm thử phải trả về kết quả rõ ràng và script phải kết thúc với exit code `0` khi toàn bộ pass, hoặc `1` khi có bất kỳ assertion nào thất bại.

### Danh mục ca kiểm thử chi tiết:

1. **[T01] Kiểm tra Fail-Closed khi AUTH_SECRET không hợp lệ (Negative Unit Tests):**
   - Trường hợp 1: `AUTH_SECRET` là `undefined` hoặc rỗng `""`.
   - Trường hợp 2: `AUTH_SECRET` chỉ chứa khoảng trắng `"   "`.
   - Trường hợp 3: `AUTH_SECRET` có khoảng trắng đầu hoặc cuối `"  secret_du_32_ky_tu_nhung_co_space  "`.
   - Trường hợp 4: `AUTH_SECRET` quá ngắn (`< 32` ký tự, ví dụ `"short_secret_20_chars"`).
   - Trường hợp 5: `AUTH_SECRET` trùng với các placeholder đã biết trong danh sách đen.
   - *Kỳ vọng:* `signToken()` ném `AuthConfigurationError`; `verifyToken()` trả về `null`; thông điệp lỗi không chứa nội dung của secret.
2. **[T02] Kiểm tra biến sai tên / biến cũ (Legacy Variable Rejection):**
   - Thiết lập `AUTH_SECRET` rỗng và `JWT_SECRET = "valid_length_jwt_secret_value_32chars"`.
   - *Kỳ vọng:* `signToken()` và `verifyToken()` không nhận `JWT_SECRET`, tiếp tục fail-closed an toàn.
3. **[T03] Xác thực phiên với Secret ngẫu nhiên hợp lệ (Positive Unit Test):**
   - Thiết lập `AUTH_SECRET` là chuỗi ngẫu nhiên 32 ký tự hợp lệ.
   - Ký token cho user mẫu (`id: 1, email: "admin@angimom.vn", role: "ADMIN"`).
   - Xác minh token qua `verifyToken()`: Trả về đầy đủ payload, khớp đúng `id`, `email`, `role`.
4. **[T04] Từ chối Token sai chữ ký, hỏng cấu trúc hoặc quá hạn (Tampered & Expired Tokens):**
   - Token bị chỉnh sửa 1 ký tự trong payload hoặc signature $\to$ `verifyToken()` trả về `null`.
   - Token không đúng định dạng `payload.signature` $\to$ `verifyToken()` trả về `null`.
   - Token có `exp` trong quá khứ $\to$ `verifyToken()` trả về `null`.
5. **[T05] Từ chối Token ký bằng khóa mặc định cũ (Old Fallback Token Rejection):**
   - Giả lập token được ký bằng khóa fallback cũ `'angimom_default_fallback_secret_must_be_overridden_in_production_32chars'`.
   - Xác minh token dưới runtime sử dụng `AUTH_SECRET` mới hợp lệ.
   - *Kỳ vọng:* Bị từ chối hoàn toàn, `verifyToken()` trả về `null`.
6. **[T06] Kiểm thử tích hợp HTTP Handler & Ranh giới RBAC thực tế (Integration RBAC Tests):**
   - Tạo cookie session hợp lệ cho tài khoản `role: 'COOK'`.
   - Gọi trực tiếp handler xuất bản công thức `POST /api/recipes/[id]/publish` với fixture công thức có thật.
   - *Kỳ vọng:* Nhận phản hồi HTTP 403 Forbidden ("Chỉ Quản trị viên (ADMIN) được phê duyệt xuất bản").
   - Positive control: Gọi với cookie có `role: 'ADMIN'` $\to$ Vượt qua kiểm tra quyền (không nhận 403).
   - Anonymous control: Gọi không kèm cookie $\to$ Nhận phản hồi HTTP 403 / 401.
7. **[T07] Đảm bảo không rò rỉ Secret trong Log và Error Response (Redaction Verification):**
   - Kích hoạt lỗi `AuthConfigurationError` trong luồng đăng nhập `/api/auth/login`.
   - Bắt response trả về: Mã HTTP 500, payload `{"error": "Lỗi cấu hình xác thực hệ thống"}`.
   - Kiểm tra log sinh ra qua `redactSensitiveData()`: Không chứa giá trị của secret test.
8. **[T08] Kiểm tra tính nghiêm ngặt của Docker Compose & Preflight (Config Validation):**
   - Kiểm tra file `docker-compose.prod.yml` khi không truyền `AUTH_SECRET` hoặc `POSTGRES_PASSWORD`: Lệnh validation fail với thông báo biến bắt buộc.
   - Kiểm tra khi truyền đầy đủ biến: Cú pháp compose hợp lệ.
9. **[T09] Kiểm tra Tính sẵn sàng tại `/api/health` (Readiness Probe):**
   - Khi `AUTH_SECRET` không hợp lệ: `GET /api/health` trả về HTTP 503 và `status: "unhealthy"`.
   - Khi `AUTH_SECRET` hợp lệ và DB kết nối được: Trả về HTTP 200 và `status: "healthy"`.
10. **[T10] Kiểm thử TypeScript & Production Build thực tế:**
    - Chạy `npx tsc --noEmit` $\to$ Exit code `0`.
    - Chạy `npm run build` thực tế trong môi trường không có `AUTH_SECRET` production $\to$ Exit code `0`.

## 8. Success Criteria (Tiêu chí thành công quan sát được)

1. Mọi thành phần của hệ thống sử dụng duy nhất tên biến `AUTH_SECRET`.
2. Không còn bất kỳ giá trị fallback bí mật mặc định nào trong mã nguồn hoặc compose file.
3. Khi thiếu `AUTH_SECRET`, ứng dụng từ chối ký và xác thực phiên, đồng thời `/api/health` trả về HTTP 503.
4. Token ký bằng khóa cũ bị từ chối 100%.
